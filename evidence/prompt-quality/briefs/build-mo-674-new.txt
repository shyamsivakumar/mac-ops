## Goal and why

Since #670 (MO-1112) only gatekeep launches gates, and gatekeep's gate brief never asks the reviewer for the open-findings line. The lane's brief adds `OPEN_FINDINGS_INSTRUCTION` (`coordinator/overnight/lane_driver.py:691`) from round 3 on, asking the reviewer to end with `Open critical or major findings: none` when that is true. Gatekeep's brief (`build_gate_brief` in `coordinator/bin/gate_policy.py`) never had it. So the round-3 FAIL merge rule (#626) works only if a reviewer writes the line unprompted; otherwise the PR goes to the rounds decision for Shyam.

Fix: `build_gate_brief` adds the instruction when the PR has 2 or more earlier failed gate rounds. Gatekeep counts those from its own records (FAIL verdicts on earlier heads of the same PR), the same count the lane used. Move `OPEN_FINDINGS_INSTRUCTION` to `gate_policy.py` so one copy exists, and restore check (f) of `gate-round-cap` in `selftest.py` against gatekeep's brief.

## Context

- `coordinator/bin/gate_policy.py` `build_gate_brief` builds the whole gate message. It holds no queue or ledger state, so the count of earlier failed rounds has to be passed in by the caller.
- `coordinator/bin/coordq` `gate_args` (around line 1590) is the one place gatekeep calls `build_gate_brief`. Gatekeep keeps each head's gate record under `gatedHeads` (see `has_verdict`, around line 150); a FAIL verdict on an earlier head of the same PR is one failed round.
- `coordinator/overnight/lane_driver.py:691` defines `OPEN_FINDINGS_INSTRUCTION`, and line 1331 appends it to the lane's brief when `failed_reviews(...)[0] >= GATE_ROUND_CAP - 1` (`GATE_ROUND_CAP` is 3 at line 49). Once the brief carries the instruction itself, the append at 1331 is a duplicate and goes.
- `coordinator/overnight/selftest.py` line 822 notes that the round-cap case is asserted in the `gate-round-cap` eval; check (f) there was dropped when only gatekeep started launching gates and is restored here.
