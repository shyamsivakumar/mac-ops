(1) Omissions

1. The approval protocol lacks a persisted, single-use grant binding the approval ID to the saved session, exact action, repository, and PR head; it also lacks a specified observer for decisions-card answers. `approval_request` and `approval_expired` are absent from the declared outbox/inbox kinds, and the deny-only guard has no defined way to permit an approved retry, so resume can request approval forever (§§3.2, 3.6, 3.7; §10 T11).
2. Recovery is asserted rather than specified: there is no journal-cursor schema, backfill schedule, poller bootstrap watermark, or atomic journal-to-inbox handoff. The rollback claim that the journal contains all inbox state is also false for direct polls, timers, approvals, sessions, and outbox delivery (§1 “Why the inbox lives where it lives”; §3.3; §6 Rollback).
3. The outbox dispatcher has no specified launch path, locking, retry/backoff policy, terminal-failure handling, or operator drain/replay procedure. Its delivery and alerting liveness therefore depend on an unspecified component (§3.7).
4. The metrics cannot establish “zero lost events”: terminal `failed` and stuck/failed outbox rows are excluded, and no independent source reconciliation detects facts never enqueued. Latency also changes from actual PR creation to inbox-row creation, hiding delays such as `gate_queued` arriving hours after PR opening (§§2, 3.3, 5).
5. Shadow mode finishes its seven-day evaluation before reviews, labels, CI, and timers are added; approvals are added only after cutover. Thus the riskiest producers and the entire resume path can reach live operation without the promised shadow evidence (§6 steps 2–5).

(2) Failure modes and race conditions

1. A worker wedged while holding `inbox.worker.lock` prevents every later worker from reaping expired leases, processing the fallback, or raising the age alarm. The 600-second model timeout does not bound post-model processing or the whole worker, so the design needs an independent watchdog rather than relying on the stuck worker to report itself (§3.4 invariants 2, 4, 5, 7).
2. A crash or failed SQLite write after the journal append but before `inbox.enqueue` silently loses the wake; printing to stderr does not close that window. Without a running reconciler, the proposed replay mechanism does not guarantee recovery (§3.3 “Journal events”; §1 “Why the inbox lives where it lives”).
3. Retried runs and sends are not idempotent: a crash after a board/tool mutation but before the final transaction repeats that mutation, while a crash after `coordq create` repeats queue creation. Printing the outbox dedupe key in the body makes a duplicate recognizable but does not prevent duplicate work (§§3.4, 3.5 step 6, 3.7).
4. `ci_main:<repo>:<sha>:<context>` omits the status/conclusion, so observing `pending` can permanently dedupe the later failure or success for that same commit and context. Enqueue only terminal states or include the state in the fact identity (§3.2 “Dedupe key”; §3.3 “CI on main”).
5. Immutable poll facts can return after their done row is purged: an old review on a long-lived PR or a status on an unchanged `main` head becomes a new event after 30 days. Durable source watermarks or permanent dedupe identities are required (§§3.2, 3.3, 3.4).
6. Coalescing every event for a repository/PR into only the “newest state” can erase an older but still actionable kind, such as a failed gate followed by a later review. Marking every source row done then records those discarded decisions as handled (§3.5 steps 3 and 6).
7. Cutover can leave three independent two-hour fallbacks: the inbox timer, the in-session idle wake, and optionally the old launchd tick at 7,200 seconds. They can duplicate model work instead of providing one fallback (§3.6a; §4; §6 step 4).

(3) Simpler alternatives

1. Keep the append-only journal as the event store and persist a byte offset/event ID advanced only after a successful existing full-board tick; the journal hook touches a `WatchPaths` trigger, with one two-hour fallback. This provides durable batching, crash replay, event-driven wakes, and existing `ALERT`/`NOOP` decisions without a second lifecycle database (§1 “Ownership check”; §§3.6a, 4).
2. If SQLite is retained, use only `pending`/`done` rows while holding the existing whole-pass flock, leaving rows pending on a crash for the next trigger or fallback. The single worker and hard process timeout make claimed leases, reaping, and multi-worker lease states unnecessary until actual concurrency requires them (§§3.4, 3.5).
3. Replace saved-session approval resume with an answer event that starts a fresh run and carries a one-time grant bound to the exact proposed action and head. The guard can atomically consume that grant, avoiding fragile session checkpoints, replay ambiguity, and approval loops while preserving approvals as events (§3.6).
